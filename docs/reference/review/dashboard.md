# Adversarial coverage review of the "dashboard" design

## (A) Verdict

**Sound foundation, not ready to implement.** I sampled 78 items across the three screens. About 34 are covered precisely enough to implement; the rest are in B, C and D. The compiler, DCHost, token and font, gesture-preservation, parity-harness and permission-union sections are strong. I confirmed from the decoded runtime that `data-dc-tpl` is stamped pre-order over every element, including `sc-if`, `sc-for` and `sc-helmet`. Elements whose children are all inline text get a static content-hash key suffix, so positional JSX is equivalent. Most of the sampled items I checked as correctly covered are in the compiler, shim, CSS/fonts and permission-union sections.

The weak areas are:
1. **Squarespace.** The design never says how Oasis learns of payments, and one capability premise is wrong (C-1). It also has no processor-side state in the ledger math.
2. **SMS.** It has no composer, no inbound-thread model, no visible surface for device failure, and untruthful toasts.
3. **Auth.** There are no flows beyond `/login`, and the email-login model contradicts the Settings employee form.
4. **Operations command contracts.** The guards, booking form, photos and staff eligibility are incomplete.
5. **The parity allow-list.** It omits whole categories of intended differences, so the zero-diff gate will fail on day one.

I fetched the Squarespace and SMS Gate docs to check the capability claims. The findings are folded into C and D.

## (C) Incorrect or contradictory statements

1. **Squarespace webhooks.** The task premise lists "Webhook Subscriptions e.g. order.create/order.update". Squarespace documents that the Webhook Subscriptions API requires an **OAuth token**. API keys cannot create subscriptions. API keys also require a Commerce Advanced plan. The design must either obtain an OAuth client, which goes through Squarespace's OAuth client process, or **poll** Orders and Transactions by `modifiedAfter`. Polling is the only path that needs no approval.
2. **Card-on-file display.** The design says "derived from the latest transaction's card brand/last4 when the API provides it". The Transactions API is read-only and returns payment documents. Only refunds initiated through Squarespace are captured. I could not confirm last4 in the documented fields. Plan on brand only, with "Managed in Squarespace" as the default.
3. **§4.1 Calendar row versus the replicate list.** The design says "emergency days render the closed notice". The original `dayInfo` ignores emergency state and never treats today as closed. The "today never closed" quirk appears in neither the replicate nor the fix list. The two are in direct conflict, because an emergency is almost always today. Add a decision.
4. **§6.2 replicates the 4-column photo grid with 3 slots.** The slot logic shows the add tile only while `n < 3`, so at three photos there is no add tile. That conflicts with S3 photo upload.
5. **Session `isSuperAdmin` versus view-as.** The design says the server downgrades authority to the assumed role, and the menu shows only when `isSuperAdmin`. If `isSuperAdmin` follows effective authority, the Super Admin is locked out of the menu after picking Crew. Add a separate `canViewAs` based on the real identity. Add a "Viewing as X — exit" indicator, because the effect spans Operations and Settings, which have no menu.
6. **"API checks Origin" on every mutation.** SMS Gate and Squarespace webhooks send no Origin and no `Idempotency-Key`. Carve them out (B44).
7. **§4.1 KPI "N booked".** The design defaults to appointments with status `booked` and calls the original "12 booked" coincidentally equal to the value. At seed the booked-status count is 2, not 12, so the claim is wrong. Either the default or the sentence has to change.
8. **§5.2 `page.clock.install({time:'2026-06-13T10:36:00'})`.** The string is parsed without an offset, most likely in the host's timezone, which is probably UTC. That yields 6:36 AM Eastern, not 10:36. Use an explicit offset (`-04:00`). It affects "Arriving soon" and `late` comparisons in the port versus the original's constant `NOW=10:36`.
9. **§3.2 "tsconfig target ES2022 so class fields initialise in order".** Next compiles with SWC and its browserslist, not the tsconfig target. Also, a subclass field redeclared without `declare` (for example `state: S;`) resets the base-initialised value under define semantics. Require `declare` for redeclared base fields, and add a vitest ordering test.
10. **§1.4 `color-scheme:dark` on the wrapper.** The design describes this as a fix for the date input only. A wrapper-wide `color-scheme` also changes UA styling for other controls, and so affects pixel parity on every dark screen. Scope it to `input[type=date]` in dark theme.
11. **§5.3 parity allow-list is incomplete.** It lists KPI, renewal, lifetime, payMethod and closure fields. It omits money-format changes (cents versus whole dollars across `payLabel`, `payBig`, `payRows`, KPI sums, `addonTotal`), `newSlots` and `newServices`, calendar days that the original generates procedurally, retention and credit labels, and the VIP reconciliation (B36). The zero-diff gate fails on day one without these.
12. **§3.3 `config.devTools`.** The session payload listed in §1.2 doesn't include a config object, so the flag has no source.
13. **§1.2 Settings route alias.** `/settings/[section]` uses `getServerSideProps` with `dynamic ssr:false` pages. This is fine, but hash-only links need `router.push('/settings#emergency')` to update the URL before mount. Add that as a test case, since the original handled only `#emergency`.

## (D) Risky assumptions and mitigations

| Risk | Detail | Mitigation |
|---|---|---|
| **Squarespace ingestion** | OAuth-only webhooks. API keys need Commerce Advanced. The Transactions endpoint takes `modifiedAfter`, `modifiedBefore` and a cursor, and returns 50 documents per page. Refunds made outside Squarespace aren't captured. | Build a polling sync (1 to 5 minutes, cursor and watermark, idempotent upsert) as the baseline. Treat webhooks as an optimisation once an OAuth client exists. Confirm the plan tier and rate limits before sizing the poll. |
| **Payment link amounts** | The API cannot create arbitrary-amount checkout or invoice links. | Keep the pasted-URL input. Make unmatched payment links visible in the unmatched queue (B4). |
| **Processor-controls gap** | Anyone with Squarespace admin access can refund without Oasis limits. | State it. Alert on external refunds (B3). Offer the Stripe-connected-to-Squarespace option as the documented later fallback. |
| **SMS Gate over Tailscale** | Local server supports Basic auth only. Webhooks to private IPs need HTTPS with a valid cert (Tailscale `.ts.net` cert via `tailscale cert` or `serve`). The tablet's Tailscale app can be killed by Android Doze. | Disable key expiry for the tablet and backend nodes. Enable MagicDNS and HTTPS in the tailnet. Exempt both apps from battery optimisation. Keep the tablet on power. NTP sync for the HMAC timestamp. |
| **Port and cert conflicts** | A public Caddy on `:443` and a tailnet-facing listener for the tablet. | Give the tailnet listener its own hostname and, if needed, port. Caddy can obtain `.ts.net` certs if permitted. Test before building the adapter. |
| **Android SMS rate prompt** | Stock Android limits an app to roughly 30 outgoing SMS per 30 minutes before prompting for confirmation (device dependent). Emergency broadcasts exceed this. | Throttle the queue below the limit, prioritise by customer arrival time, or whitelist the app on the tablet. Surface queue depth and ETA. |
| **Carrier filtering** | A SIM-based gateway is person-to-person traffic. High volume, links and templated text can be filtered. Delivery reports may never arrive. | Treat `sent` as success and `delivered` as a bonus. Keep messages short, avoid shortened links, log failures. The `SmsProvider` interface allows a fallback. |
| **Single device** | The tablet is a single point of failure. | Persist the outbound queue. Alert early (B20). Document a manual-send fallback. |
| **Playwright on aarch64 AL2023** | Needs `PLAYWRIGHT_HOST_PLATFORM_OVERRIDE`. Chromium downloads for arm64 change between Playwright releases. | Pin the exact Playwright version. Run `parity:setup` as a gate. Record the working version in the repo. |
| **Native modules without gcc** | Auth and password hashing libraries may need compilation. | Prefer prebuilt arm64 binaries, or install `gcc-c++ make` from dnf upfront. |
| **Next 15 plus React 18 support window** | Next 15 is the last line supporting React 18. Next 16 requires newer React. | Check the Next support policy and the date. Plan an upgrade path behind the parity suite. |
| **2 vCPU and 7.8 GB** | Next build, `tsc`, Postgres, Chromium (two pages for parity) and the API compete. | Never run the parity suite and a build together. Add swap. Keep `--max-old-space-size=3072`. Run `@full` nightly. |
| **Parity at threshold 0** | Software rasterisation and `backdrop-filter` can be nondeterministic. The rAF-batched store notifications and 250 ms invalidate window run under a fake clock. | Disable batching in the parity build. Keep `parity/tolerances.json` with reasons. Run the original-versus-original determinism gate first. |
| **ScreenStyle timing** | Styles injected "on mount" can flash unstyled content during client route changes. | Inject in `useLayoutEffect`, dedupe by `data-oasis-screen`, and test route transitions. |
| **CSP** | The design lists `font-src`, `style-src` and `frame-ancestors` only. | Add `script-src` (nonce or hash for the `_document` theme script and Next bootstrap) and `connect-src 'self'` for SSE. |

## (E) Top 10 changes before implementation

1. **Decide the Squarespace ingestion architecture.** Use polling as baseline and OAuth webhooks as optional. Confirm the plan tier. Define the order-to-invoice correlation key, the unmatched queue and the method taxonomy (B3–B5, C-1).
2. **Add the processor-pending ledger state** with effects on `paid`, `balance`, `refundable`, status and KPIs, plus a staff-confirm control (B1, B2).
3. **Make SMS usable.** Add a real composer, inbound threading and truthful toasts. Normalise encoding. Handle the Android send limit. Surface device and sync failures globally, not only on Bay Board (B15–B21, D).
4. **Complete the auth model.** Add invite, reset and expiry flows. Resolve the email-versus-phone login contradiction. Fix the view-as trap. Add last-Super-Admin guards (B22–B24, C-5).
5. **Fix Settings permissions.** Complete the section-to-key map, filter the bundle, redact pay rates, and add an explicit staff-eligibility flag (B25, B26).
6. **Finish the Operations command contracts.** Write the 409 guard list, the booking form semantics (date, walk-in, parse, upsert), the package list decision, the availability algorithm, photos (including the 3-slot contradiction), and calendar closed-day rules (B28–B32, B34, C-3, C-4).
7. **Rebuild the parity allow-list and harness settings** before compiling. Cover money cents, new slots, generated calendar days and retention. Fix the clock timezone. Disable rAF batching in the parity build (C-8, C-11, D).
8. **Resolve seed and invoice decisions.** Settle invoice creation and numbering, VIP and title reconciliation, and which KPIs read from the ledger (B11, B12, B36).
9. **Specify ingress topology.** Cover public versus tailnet exposure, webhook routes outside the Origin and idempotency checks, the dual-hostname proxy, SSE heartbeats and `resync`, and the CSP script policy (B38, B44, C-6, D).
10. **Add the background-jobs and event inventory,** with owner and emitted SSE event for each: auto-reopen, late detection if server-side, VIP release, federal holidays, credit expiry, membership cycle, sync polling (B21, B27, B39).
