# 0006 Error model and idempotency

Status: accepted (2026-10-06)

**Errors** are RFC 9457 `application/problem+json` with a machine-readable `code`, `errors[]` field paths for validation
and a `requestId`. For guard failures `title` and `detail` are exactly the design's toast strings, kept in one catalog
(`src/platform/errors.ts`) so the dashboard toasts them unchanged and copy is reviewed in one place. Status mapping:
400 malformed, 401, 403, 404, 409 state conflict, 412 version mismatch, 413, 415, 422 validation or business rule, 429.
Unknown failures are 500 `INTERNAL` without internal detail.

**Idempotency** is mandatory on every money-effecting route (and appointment creation and emergency close), with the key
generated by the client when the sheet opens and reused until success or cancel. The key is claimed in its own committed
statement (`in_flight`, 2-minute lock so a crashed process cannot wedge a key), the command runs in one transaction, and
the response is stored inside that same transaction, so a committed mutation always has its replayable response and a
crash never leaves a half state. Keys are scoped per user and hash method, path (sorted query) and canonical body (key
order irrelevant); same key with a different request is 422 `IDEMPOTENCY_MISMATCH`, a duplicate while running is 409
`IDEMPOTENCY_IN_FLIGHT`, replays carry `Idempotent-Replayed: true`, rows expire after 48 hours. Failed commands release the
key because their transaction rolled back, so a corrected retry is not punished. Routes declared `idempotency: 'required'`
must be built with `idempotentHandler`; this is checked at boot, so a money route cannot ship without it. Webhooks are
exempt (they de-duplicate on `webhook_log (provider, external_id)`).

Alternatives rejected: storing the response after the transaction (a crash between commit and store would allow a double
effect); blocking a duplicate until the first finishes (hides contention and holds a connection); keeping failed responses
(punishes validation retries).
